# 0015 — Installer stack: a Rust core, the Interleaf web form, LVGL on the device later

## Context

The installer ([0014](0014-installation-and-provisioning.md)) runs in a browser, on Linux
and Windows, and on a PC started from removable media. It talks to devices over USB
(fastboot, adb) and to a PC's disks, partition tables and firmware variables. The GlassineOS
recovery ([0007](0007-recovery-mainline-twrp.md)) runs its repair and reinstall, on arm64
with musl and no large runtime. It writes partitions, so its plan checks and failure tests
have to be cheap to write and hard to get wrong.

The organization already has one design system, Interleaf, in the `ui` repository, with a
form generated from its tokens for each way of drawing: a web form (the documentation
site, the hub), a cairo C library (the shell, Home) and a cairo Python package (Settings,
first-run setup). Every new way of drawing adds a form to keep current.

## Decision

- **One core, in Rust.** Device descriptions, the plan, the platform backends and the
  device protocols are one library. It builds as a static program for Linux and Windows,
  for arm64 musl (the recovery), and to WebAssembly (the browser). USB goes through a
  library that works both natively and over WebUSB. Rust becomes one of the
  organization's languages for this core and the tools around it.
- **Every interface is a client of the core.** A thin command line for CI and developers;
  the screens for people.
- **The screens are web pages on Interleaf's web form**, built like the hub's front end:
  Preact and htm as plain modules, no build step, the styles generated by `ui`. No new UI
  framework and no new form in `ui`.
- **Browser first.** The browser version loads the core as WebAssembly and reaches devices
  over WebUSB, which only Chromium-based browsers offer. A desktop wrapper for Linux and
  Windows uses the same pages in the system's web view; which wrapper is not decided.
- **On a PC from removable media**, the installer runs inside a GlassineOS live session,
  which also lets the person try GlassineOS before installing it.
- **Device descriptions are TOML files with a schema**, checked by the core's own validator
  in CI and before use.
- **LVGL is for the tooling that runs on the device itself**: the GlassineOS recovery, and
  later boot-time tools and a bring-up kit for new devices. It draws on a bare framebuffer,
  with no compositor or browser. It is added to `ui` as Interleaf's fourth form when the
  recovery is built, not before. The installer doesn't use it.
- **One form per way of drawing.** A new program uses an existing Interleaf form. A new form
  is added only for a way of drawing that a product needs and no form covers.

## Consequences

- The installer, the recovery's repair and reinstall, and CI run the same code, so there is
  one implementation of every plan and check.
- A token change reaches the installer the way it reaches the hub and the documentation.
- Two things need a spike before the core is built on them: fastboot from Rust over WebUSB
  (asynchronous only, Chromium only), and Windows USB drivers. A device that needs a
  driver the person would have to install by hand must be detected and explained, never
  left to a command line.
- The GlassineOS recovery brings LVGL and its form with it; until then, nothing in the
  organization draws with LVGL.

## Status

Accepted 2026-11-12.
